# Skill Bridge Flask backend

This Flask backend uses the approved Supabase tables instead of local JSON files
and process-memory lists for active API operations.

## Setup and run

From this directory in PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python scripts\check_supabase_connection.py
python app.py
```

The connection check initializes the Supabase Python SDK and checks only the
Supabase Auth health endpoint. It does not query or change database rows.

The existing `.env` file must define:

```dotenv
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_KEY=your-supabase-publishable-key
```

Use the publishable key, never a service-role/secret key or database password.
`.env` is ignored by the repository `.gitignore`; `.env.example` contains
placeholders only.

## Authentication

Protected API calls must include:

```http
Authorization: Bearer <Supabase access token>
```

Flask validates the token with Supabase Auth on each request, reads the role
from the caller's own `profiles` row, and creates a separate request-scoped
Supabase client carrying that token. The frontend-provided user ID is not used
to authorize requests. RLS remains active for every data operation.

The current React prototype still uses browser-local fake login and does not
send access tokens. Its API calls will receive `401` responses until Phase 3
connects Supabase Auth and forwards the token. No frontend authentication was
changed or claimed as tested in this phase.

New Auth users receive a student profile from the Phase 1 database trigger.
The backend never promotes a user from signup metadata. A trusted project
administrator must independently verify a recruiter and approve the role in
Supabase before recruiter-only APIs are available.

## API storage

| API data | Supabase table or RPC | Access |
|---|---|---|
| Student profile | `profiles` | Student's own row |
| Student skills | `student_skills` | Student's own rows |
| Student projects | `projects` | Student's own rows |
| Company profile | `companies` | Owning recruiter |
| Jobs | `jobs` | Authenticated users can read; owning recruiter manages |
| Application tracker | `applications` | Student's own rows and private notes |
| Recruiter decisions | `candidate_decisions` | Recruiter owning the job |
| Recruiter candidate list | `get_candidates_for_job` RPC | Own job and consented students only |

Matching scores remain in the existing application logic; they are not stored
in the database. Job IDs are generated by the database sequence. The
`/students/` recruiter response includes consenting registered students only;
the existing frontend continues to supply its static demo candidates, avoiding
duplicates after those demos are imported.

Saving a student profile, skills, and projects uses several RLS-protected
requests rather than one database transaction. If a network failure interrupts
a save, retry the same full profile request to reconcile the profile data.

Existing API paths are retained: `/students/`, `/company/`, `/jobs/`,
`/jobs/<job_id>/decisions/`, and `/tracker/`. Route errors use JSON with an
`error` message and appropriate `4xx` or `503` statuses.

## Existing JSON data

Untouched source-data copies made before any import are in
`data_backups\phase2-original-json\`. The current Python student and tracker
collections were process-local only; any records lost when Flask stopped
cannot be reconstructed.

The migration tool itself was not run during Phase 2. To preview source rows
without writing files or connecting to Supabase:

```powershell
python scripts\migrate_json_to_supabase.py --dry-run
```

To create a new backup and generate an idempotent SQL import file (without
executing SQL), use a new output path:

```powershell
python scripts\migrate_json_to_supabase.py --output .\data_backups\skill_bridge_import.sql
```

Only provide `--company-owner-profile-id <UUID>` if that recruiter profile's
company ownership has been independently verified. Review the generated SQL
and its report before manually executing it in the Supabase SQL Editor as a
trusted database owner. The script does not use a service key or connect to
Supabase. It preserves job IDs, inserts missing records only, and synchronizes
the job sequence. Existing company JSON has no verified owner and currently
contains only a placeholder, so it is reported as skipped. Registered-user
decisions are imported only if their email resolves to an existing profile.

The script imports the backend's active `jobs.json` and the demo
`src\data\candidates.json`; it backs up the frontend's duplicate sample
`src\data\jobs.json` for reference but does not import duplicate job IDs.
Existing JSON files are never changed or deleted.

## Tests

```powershell
python -m unittest discover -s tests -v
```

The tests use fake Supabase clients and fixtures. They do not use real student
or recruiter accounts, connect to the database, or verify live RLS behavior.
